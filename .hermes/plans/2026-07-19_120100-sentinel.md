# Sentinel Implementation Plan

> **For Hermes:** Execute this plan task-by-task with TDD and spec/code review after each milestone.

**Goal:** Build a reproducible SigNoz-native control loop that detects runaway AI/MCP agents from OpenTelemetry signals, quarantines their credentials, and records evidence for human recovery.

**Architecture:** Foundry deploys SigNoz and its MCP server. A small Python webhook receiver accepts signed SigNoz alert notifications, validates/deduplicates them, applies a fail-closed quarantine action through a pluggable revoker, exports control-loop telemetry back to SigNoz, and sends a concise notification. A deterministic demo workload emits normal traffic followed by a repeated-tool-call incident so judges can watch detection → alert → quarantine → recovery.

**Tech Stack:** Python 3.11 stdlib-first, OpenTelemetry OTLP HTTP, SigNoz Foundry, Docker Compose patch, YAML policy, pytest only if already available (otherwise `unittest`).

---

## 0. Product boundary and winning claim

**One-line pitch:** SigNoz does not merely observe a runaway agent; Sentinel turns its telemetry into a reversible circuit breaker.

**Non-goals for hackathon week:** generic MCP gateway, LLM-based RCA, multi-tenant IAM platform, Jira integration, arbitrary policy DSL, Kubernetes support.

**Safety boundary:** quarantine is reversible; destructive remediation is forbidden. Production mode must use authenticated webhooks, an allowlist of credential IDs, idempotency, audit logs, and dry-run as the default.

**Success metrics:**
- Detection-to-quarantine latency under 5 seconds in the local demo.
- Duplicate alerts cause exactly one quarantine action.
- Forged or stale webhook requests cause zero actions.
- Every action emits an OTel span/metric visible in SigNoz.
- Fresh clone reproduces deployment using committed `casting.yaml` and `casting.yaml.lock`.

### Task 2: Model and validate SigNoz alert events

**Objective:** Convert untrusted webhook JSON into a small validated incident object.

**Files:**
- Create: `src/sentinel/model.py`
- Create: `tests/test_model.py`

**Required behavior:**
- Require `status`, `alertname`, `startsAt`, and labels containing `agent_id` and `credential_id`.
- Accept only firing alerts for action; resolved alerts become no-op recovery events.

- Normalize timestamps to UTC.

**TDD:**

### Task 3: Authenticate and freshness-check webhooks

**Objective:** Prevent arbitrary callers and replayed payloads from quarantining agents.

**Files:**
- Create: `src/sentinel/auth.py`
- Create: `tests/test_auth.py`

**Protocol:**
- Headers: `X-Sentinel-Timestamp` Unix seconds, `X-Sentinel-Signature` hex HMAC-SHA256.
- Signed bytes: `<timestamp>.` + exact request body.
- Reject timestamps outside ±300 seconds.
- Compare signatures with `hmac.compare_digest`.

**TDD:** valid, altered body, wrong secret, stale timestamp, missing headers.

**Verification:** `python3 -m unittest tests.test_auth -v`; expected: all pass.

**Commit:** `feat: authenticate alert webhooks`.

### Task 5: Define reversible revocation adapters

**Objective:** Separate control-loop behavior from the exact SigNoz credential API, whose endpoint must be verified before enabling production mode.

**Files:**
- Create: `src/sentinel/revoker.py`
- Create: `tests/test_revoker.py`

**Adapters:**
- `DryRunRevoker`: records intended action and always returns evidence.
- `HttpRevoker`: calls configured revoke URL using stdlib `urllib`, bearer admin token, timeout, and strict 2xx handling.
- `release()` mirrors `quarantine()` for judge-visible recovery.

**Important:** do not guess a SigNoz key-revocation endpoint. Keep `HttpRevoker` endpoint configured via `SENTINEL_REVOKE_URL` until confirmed against the live installed API. Demo uses a local credential-broker endpoint if SigNoz has no supported revoke API.

**TDD:** dry run, successful HTTP response, timeout/failure, no secret leakage in errors, release path.

**Verification:** `python3 -m unittest tests.test_revoker -v`; expected: all pass.

**Commit:** `feat: add reversible quarantine adapters`.

## Build order and stop/go gates

**Gate A (after Task 5):** confirm the real SigNoz/service-account revoke path. If unsupported, use Sentinel-issued scoped MCP credentials via a tiny local broker; do not claim native SigNoz-key revocation.

**Gate B (after Task 9):** fresh Foundry deployment must work with committed lockfile. Stop feature work until reproducibility passes.

**Gate C (after Task 10):** the real SigNoz alert must trigger the real webhook. Synthetic alert-only demos are insufficient.

**Gate D (before submission):** score every criterion at least 80/100 with a linked artifact; presentation and UX must have screenshots/video verified visually.

## Risks and mitigations

- **MCP server telemetry lacks tool fingerprints:** instrument the demo agent with OTel GenAI/MCP semantic attributes; never invent data.
- **No supported key revocation API:** quarantine a Sentinel-controlled scoped credential/broker, and describe the boundary accurately.
- **Alert webhook lacks signing headers:** place a shared secret in the webhook URL/header if SigNoz supports custom headers; otherwise bind locally and use a reverse proxy that signs forwarded events.
- **Foundry patch paths change:** pin Foundry version and commit `casting.yaml.lock`.
- **False positives:** repeated identical tool + argument hash and threshold window; dry-run default; manual release.
- **Category saturation:** pitch the verifiable closed control loop, not generic MCP observability or rate limiting.
